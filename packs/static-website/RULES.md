# Static website

- **A published file is a file the publish set names — adding a page is two edits.** The Pages artifact is assembled from `.github/site.config`'s `publish_paths` and nothing else, so a new page, stylesheet or data file that isn't under a published path (or named in the list) is simply absent from the live site, with no error anywhere: the build is green, the deploy succeeds, the page 404s. When you add a file the site serves, put it under an already-published directory or add it to `publish_paths` in the same change. The list is additive on purpose — the alternative, "publish the repo minus what we remember to exclude", publishes every draft, note and key nobody thought to hide.
- **The site is served from a subpath, not a domain root.** GitHub Pages serves it at `https://<owner>.github.io/<repo>/` (unless a custom domain is configured), so a root-relative URL — `/style.css`, `/img/logo.png`, a `fetch('/data.json')` — resolves above the site and 404s in production while working fine in a local `file://` or `python -m http.server` preview. Write links, asset paths and fetches **relative** to the page.
- **Don't call missing data survivable until you have followed it to the pixel.** "The fetch is allowed to fail — it'll just show as unknown, which we already handle" is a claim about every consumer downstream, and it is usually wrong: an absent value reaching a boolean, a comparison or a status lookup is very often indistinguishable from a real negative, so the page renders a confident falsehood with nothing logged and the visitor acts on it. Trace the missing value all the way to what it draws before deciding a failure is tolerable. Where it isn't, the file is required — fail the load and show the error state, because a wrong answer with no error is worse than an error.
